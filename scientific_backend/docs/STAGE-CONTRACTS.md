# Implemented stage contracts and evaluations

Team TBD uses the OpenAI Agents SDK for model/tool turns. Application code owns role order, tool authority, accepted evidence, work products, stopping conditions and durable state. This document describes the implemented service, including its limits; a role label or a passing software check is not proof of scientific validity.

`app/process_contract.py` supplies the versioned graph pinned at run creation. `app/stage_evaluation.py` evaluates handoff contracts. `app/worker.py` persists evaluation receipts in the same transaction as accepted work, and saves a rejected receipt before returning a product to its sender. Provider orchestration and specialist repair loops live in `app/providers.py`. The active pinned contract is available in each run export and from `GET /api/process-contract` for new runs.

Current contract `team-tbd-resistance-4` adds [hypothesis governance](HYPOTHESIS-GOVERNANCE.md): stable scoped hypothesis states and one reviewer-selected registered action between full team cycles. The per-operation role graph and acceptance boundaries remain in force. Older runs retain their pinned contract; an updated skill does not opt them into automatic execution.

## Shared handoff boundary

Every work product must carry its sender and registered recipients, case ID, exact input versions, question, method, result status, result, limitations, claims and decision it could change. The application checks:

- Case and original-hypothesis identity; unique accepted evidence IDs; packet digest and individual source/derivation hashes.
- Nonempty descriptive fields and explicit limitations; `completed`, `blocked` or `inconclusive` status. Every stated claim needs nonempty citations from the declared input packet.
- Registered sender-to-recipient routes and the required accepted upstream roles from the **same operation**. A prior decision's products cannot satisfy a new correction's dependencies.
- Current role-specific skill receipts and exact skill hashes/versions when a model was called. Skill loading establishes instruction provenance, not execution of a model or a NVIDIA service.
- At most an initial handoff attempt and one repair for each role in an operation. An accepted product cannot be silently replaced. Further revisions require a new operation.

Acceptance assigns the work-product ID and an `acceptance_evaluation_id`. Rejection returns the receipt ID, failed check names and `repair_allowed`; the model receives bounded repair feedback. Provider repairs do not gain new tool authority. An exhausted repair budget is a failed stage, not permission to publish an unsupported product.

An accepted `blocked` product is useful: it records the missing input for downstream reasoning. Its substantive question remains unanswered. For example, no exposure data yields a blocked pharmacology product that translational science must consume as an evidence gap, never as support against an exposure mechanism.

## Stage-by-stage execution

The current execution order qualifies available data before clinical framing. The clinical question still comes from the user's preserved hypothesis; the clinical specialist clarifies population and endpoint meaning after seeing the available measurement scope. This is a bounded dependency graph, not a simulation of a laboratory or a free-running conversation among all roles.

Role-specific scientific instructions and the independent review assess content quality. Deterministic software can check provenance, scope and required fields; it does **not** prove that a cited record logically supports every interpretation. Scientist review and a discriminating experiment remain necessary for scientific conclusions.

## Four loops and their stop rules

| Loop | Trigger and continuation | Stop and recovery |
| --- | --- | --- |
| L1: hypothesis testing and correction | A rejected product returns once; a concrete reviewer gap can trigger a bounded diagnostic. Under the pinned governance policy, a reviewed informative next test can become a separate qualified follow-up operation. Evidence is accepted before citation. | At most one handoff repair per role and two reviewer diagnostics per operation. A diagnostic alone does not rerun the team; an accepted governance follow-up does. Reuse completed work and stop on explicit scientific/operational limits. Advisory spending thresholds warn and continue. |
| L2: scientist correction | Correction must target the current decision version and a stable request key. A new operation reruns the team with the previous decision and attributed correction while retaining the original hypothesis. | Previous decisions/work products/receipts remain immutable. Stale versions and conflicting duplicate keys fail. The new operation has its own stage-attempt budget. |
| L3: returned measurement | Submission must match current decision, experiment and candidate IDs, with finite value, unit and notes. A new operation assesses the attributed user report. | Identity validation is not assay QC or independent verification. No synthetic observation is silently substituted. Missing controls, replicates or assay provenance remain scientific limitations. |
| L4: reusable procedure | Proposal pins the exact origin decision; scientist review precedes evaluation on a disjoint case with matching baseline/candidate context and an excluded-case control. Release rechecks immutable hashes. | No automatic promotion from one successful-looking run. The quality judgment is scientist-attributed; software checks scope, identity, mode, isolation and versions. Approved releases are procedural only; suspension prevents future retrieval. See [LEARNING.md](LEARNING.md). |

Numerical computation is deterministic for a selected recipe and input version. Model-directed selection, interpretation, review questions and experiment choice can vary. This allows investigation without manufacturing random numerical results.

## Reviewed continuation between operations

The outer hypothesis-testing policy extends L1 across reviewed operations while retaining the separate L2–L4 triggers. Specialists propose informative work; coordinator and reviewer maintain `possible`, `probable` and `clearly_ruled_out` judgments with stable IDs, source ownership, scope and accepted evidence. Biological probability/exclusion cannot rest on predictions alone. Rule-out needs a performed falsification and contradictory evidence; missing data, bad QC or nonsignificance do not establish it. An accepted software contract cannot prove that the cited result is scientifically sufficient.

With the hash-validated live `auto_continue` policy, the reviewer selects one ready, unperformed registered action targeting a possible/probable hypothesis. Publication and queue selection commit together; the executor rechecks pinned identities, saves intent, accepts qualified results and starts a new full specialist/reviewer cycle. All roles receive previous governance; required upstream products are generated again within the new operation. This differs from a bounded reviewer diagnostic, which reassesses its own result without automatically rerunning every role.

The next decision continues or records a specific reason to stop. Possible hypotheses prevent `resolved_within_scope` and require explicit blockers at a stopping point. A stopped decision cannot simultaneously nominate a ready, unperformed final test. Actual cancellation, execution failure and provider uncertainty live in `governance_state`/`governance_transitions` without rewriting the last scientific decision. Registered same-input attempts are not automatically replayed; completed work is reused. Manual modeling-only updates preserve `prior_governance` and do not claim a new scientific assessment or queue continuation. See [HYPOTHESIS-GOVERNANCE.md](HYPOTHESIS-GOVERNANCE.md) for history and manual-policy details.

## Execution budgets and recovery

`TEAM_TBD_BUDGET_MODE=advisory` is the default. Cumulative provider input/output/request/tool thresholds and outer worker time/tool thresholds warn and continue; `enforced` mode makes them stop conditions. The outer worker tracks elapsed time and emitted tool operations through `ROSALIND_MAX_SECONDS` and `ROSALIND_MAX_TOOL_CALLS` (`app/config.py`). The provider separately tracks model requests, observed tokens and actual function calls (`app/providers.py`). These are separate counters: event counts are not token counts or exact provider function-call counts. Advisory mode is not a dollar ceiling. Usage and one durable warning per provider category remain visible, and user cancellation remains available.

Each model turn for a specialist, coordinator or reviewer still sends `TEAM_TBD_AGENT_MAX_OUTPUT_TOKENS` as the technical API output allowance including reasoning (default 8,000; integer range 2,048–16,000). This per-response setting applies to tools-disabled repair and discovery finalization in both modes; it is separate from cumulative spending thresholds. The capability probe uses 2,048 output tokens. `TEAM_TBD_MAX_OUTPUT_TOKENS` sets the total observed output threshold (default 60,000; integer range 16,000–200,000); `TEAM_TBD_MAX_INPUT_TOKENS` sets the shared observed input threshold including repeated context (default 400,000; integer range 50,000–1,000,000). Input/output usage is learned from returned responses. Advisory mode warns when actual usage reaches its threshold. Enforced mode stops subsequent requests and requires the next full output allowance to fit before dispatch. The shared request/tool thresholds are 40 and 60. All settings and the selected mode are validated and frozen for the session, then preserved in budget metadata alongside alerts.

Enforced cumulative budget exhaustion persists `budget_exhausted`; advisory threshold crossings do not stop a run. Scientific stage scope remains enforced: the initial bioinformatics analysis/call limit, SDK turn and repair caps, and two reviewer diagnostic cycles are contracts, not spending thresholds. Actual provider errors, incomplete API responses and role/API timeouts remain errors in either mode. Accepted partial evidence, request IDs and charged usage survive failures. The harness does not issue a final biological conclusion merely because execution stopped. The first broad live CAR-T run exposed the earlier enforced budget path; see [VALIDATION.md](VALIDATION.md) for its actual receipt and subsequent work.

One renewable worker lease protects the SQLite database. A provider action saves intent under a stable operation-derived ID before dispatch. Successful saved results can be reused. Worker interruption after intent becomes `unknown`; it is never automatically resubmitted. A timeout does not prove that a provider stopped. Cancellation prevents new submissions but may leave dispatched remote work running. The service does not yet reconcile asynchronous NVIDIA jobs automatically.

The SDK conversation is not a durable checkpoint. The application persists objective, case context, tool evidence, work products, request records and decision versions; it does not promise to resume an interrupted model reasoning trajectory. Keep database and artifact backups together.

## Evaluation receipts and regression checks

`GET /api/runs/{id}` and JSON export include `stage_evaluations`. Each receipt has its schema, stage, verdict, substantive result status, checks, timestamp, operation/run IDs, pinned hypothesis/process hashes and its own content hash. Handoff receipts also contain attempt number and whether a repair is allowed. Rejected submissions are durable. Accepted work products link their receipt; decision-publication receipts hash the immutable decision. Existing runs made before this feature have no retroactively invented receipts.

Receipt stages are `handoff:<role_id>`, `evidence_acceptance`, `decision_publication`, `molecular_comparison` for an incomplete explicit pair, and `operation_stop`. `accepted` describes the software contract. `result_status: blocked` or `inconclusive` continues to describe the scientific or execution result. `scientific_validity` is explicitly `not_established_by_contract_checks`.

| Evaluation scenario | Required observed behavior | Automated coverage |
| --- | --- | --- |
| A statistician skips the bioinformatics handoff | Reject before accepting the product; identify missing dependency | `tests/test_stage_evaluation.py` |
| A blocked bioinformatics stage hands off its missing-input account | Accept the valid contract while keeping result blocked | `tests/test_stage_evaluation.py` |
| A product has wrong source/hash, unaccepted citations, wrong case, role route or stale upstream operation | Reject; do not append a work product | `tests/test_work_products.py`, `tests/test_stage_evaluation.py` |
| A sender submits invalid work, repairs it, or keeps retrying after two failures | Persist each rejection; permit one repair; prohibit additional accepted submissions | `tests/test_stage_evaluation.py` |
| A model omits or changes the role's applied skill version | Reject regardless of fluent content | `tests/test_scientific_skills.py`, `tests/test_worker_providers.py` |
| Provider cumulative threshold is crossed | Advisory mode emits one warning per category and continues with tracked usage; enforced mode preserves `budget_exhausted`, usage and request receipts | `tests/test_providers.py`, `tests/test_stage_evaluation.py` |
| A NVIDIA pair member remains pending, cancellation arrives, or an external write is uncertain | No completed pair evidence; retain partial artifacts and unknown intent without blind replay | `tests/test_worker_providers.py`, `tests/test_work_products.py`, `tests/test_harness.py` |
| All nine roles execute with valid tools, receipts and handoffs | Nine durable accepted products and a versioned decision | Actual SDK with mocked HTTP transport in `tests/test_worker_providers.py`; separate real provider acceptance must be recorded independently |

Run focused checks with `.venv/bin/python -m pytest tests/test_stage_evaluation.py tests/test_work_products.py tests/test_worker_providers.py tests/test_scientific_skills.py -q`. These tests use isolated state and explicit provider mocks. They establish software behavior, not GPT-Rosalind entitlement, a real BioNeMo prediction, general scientific reliability or causal discovery performance.

## Handoff for the next engineer

Keep the pinned contract and the implemented provider graph synchronized. A new role or dependency needs its route, upstream contract, scoped tools, skill version and failure-path test. Do not add model-selected paths, shell commands or endpoints to bypass the registered data/executor boundary. Update source and skill manifests intentionally; changing bytes during an operation must fail instead of silently changing its scientific basis.

For analysis expansion, add an approved recipe and meaningful numerical tests against a qualified input, then expose only its typed parameters. For scientific evaluation, add disjoint cases with scientist-reviewed outcomes and repeated stochastic runs; report how often the system chooses useful discriminating evidence, maintains alternatives and handles unavailable inputs. A passing schema check alone is not that benchmark. For provider acceptance, retain real model identity, request IDs, usage and validated artifacts. Astra high is the explicitly authorized Rosalind placeholder; do not rename an Astra call as a Rosalind call.

## Bounded discovery finalization

The initial bioinformatics stage permits at most 22 function calls and four reserved analyses, preserving scope for later roles. The model is directed to choose at most two studies; that study-selection instruction is not an additional server-enforced identity constraint. Catalog responses are paged. If six exploration turns finish without a work product, one tools-disabled finalization receives the original task and accepted evidence; normal schema, source, skill and handoff acceptance still apply. This does not grant another analysis or handoff repair. Cumulative request/token/time thresholds warn in advisory mode or stop in enforced mode; stage contracts and actual provider failures remain distinct stop conditions.

## Selected follow-up acceptance

The coordinator and reviewer author concise evidence-cited insights and recommendations against the registered recipe catalog. Publication validates both; the server assigns recommendation IDs and checks current execution prerequisites. Manual scientist selection or accepted automatic governance selection freezes the current decision, hypothesis, recipe and source-manifest hashes in a serialized operation, retaining the actual selection origin. Its executor must return qualified evidence before a new team/reviewer cycle begins. A previously completed selected analysis satisfies the initial analysis requirement, but bioinformatics must read its accepted evidence; it cannot merely reuse an earlier work product. The new operation issues new handoffs and an immutable decision version. Full endpoint, provenance and scientific-scope contracts are in [FOLLOWUPS.md](FOLLOWUPS.md).

Public CD19 isoform structure follow-ups are separate from target-retained CAR-binder comparisons. Accepted public monomer evidence permits a scoped molecular review with citations even when binder modeling is blocked. A pending member prevents pair evidence and decision publication; validated individual outputs may still be viewed with their partial status. A new recipe cannot execute against an old snapshot lacking its exact source pins.
