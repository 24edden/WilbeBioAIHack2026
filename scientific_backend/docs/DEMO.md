# Team TBD presentation guide

## Prepare

The hypothesis composer starts blank. Type or import the scientist’s question, or explicitly choose **Load CD19 example**; the source is retained and changing the evidence collection does not replace the supplied text.

Start the service and confirm **Service connected** and a live worker. Select the explicit configured model: **GPT-6 Astra · high reasoning (Rosalind placeholder)** for the user-authorized placeholder, or GPT-Rosalind only when that actual endpoint is entitled. Pass **Check model connection** before presenting. The check is a real model/tool round trip; it does not start an investigation.

Keep a completed real investigation available in history. A new live run can take several minutes because it performs scoped analysis and review; do not promise a fixed five-minute completion. A saved run must be described as a saved run, with actual timestamps and model identity. Keep a JSON export as a separate auditable artifact.

## Walk through the product

| Scene | Show | Explain |
| --- | --- | --- |
| The question | Original hypothesis and source | A scientist supplies the objective. Imported and typed wording stays intact; model alternatives are labeled separately. |
| Available data | CAR-T discovery and Data catalog, when the registry is installed | The catalog indexes registered Brev collections. The model chooses relevant files and approved analyses; indexed does not mean every file was analyzed. |
| Real execution | Start **Live investigation**, then inspect the live operations overview | The current role, latest accepted scientific result, recent actions and recorded counts come from persisted events. Spinners identify only genuinely active roles. No silent offline fallback occurs. |
| Specialist collaboration | The agent cards at the top and Work products | Seven specialists, coordinator and reviewer exchange contracts with pinned inputs, limitations and recipients. Missing patient timelines or exposure data block those branches honestly. |
| Skill use | Skills registry and current-run receipts | Show exact version/hash, role and operation. A load receipt proves loaded instructions; model receipts and accepted analyses establish their separate execution facts. |
| Source support | Evidence and completed analysis | Open a source locator and inspect computed values. State the sample/construct unit and limitations. A reporter-library result is not an individual patient's finding. |
| Findings | Findings overview and evidence-linked insight cards | Read the exact recorded finding, why it matters and the next question. Old decisions without insights show recorded claims; they are not relabeled as newly generated insights. |
| Follow-up | Model-recommended analysis cards below the full assessment | Show the proposed analysis, decision it could change, prerequisites and current readiness. Click an executable card to run an approved operation on the same investigation, then watch the next decision version. Registered legacy options are labeled separately from model recommendations. |
| Review | Assessment, alternatives and recorded reviewer diagnostics | Review may request another bounded analysis. Do not claim a diagnostic occurred when the trail does not contain it. |
| R&D | Next experiment and handoff | Explain what positive, negative and inconclusive results would change. A proposed protocol has not been executed. |
| Scientist correction | Submit a real correction and inspect v2 | Earlier versions remain immutable; the model reassesses within the original objective. |
| Learning | Propose a procedure from the current decision | It remains provisional until scientist review, disjoint evaluation and explicit scoped release. Never invent a passing evaluation. |
| Audit | Download Markdown and JSON | Hypothesis, source records, versions, handoffs and events are the persisted investigation. |

For a focused CD19 run, the pinned reporter-library packet is a useful example. Its join/QC analysis can show matched and unmatched RNA/DNA barcode identities. Read exact values from current evidence instead of reciting them as results of every discovery run.

The default run view exposes accepted handoffs during execution, their stated scientific rationale, evidence citations, limitations and software contract checks. These are public work products, not private model reasoning. The execution trail initially shows its latest 12 events; expand it for the full history. Aggregate budgets in advisory mode produce visible warnings rather than stopping the workflow; per-response model allowances and scientific/provider qualification still apply.

## Measurements and BioNeMo

Use genuine returned measurements only when provenance is available. If demonstrating the outcome form with practice input, create a separate presentation run and put **“Synthetic presenter input for workflow demonstration only; no experiment performed”** in the notes. Use exact registered experiment and candidate/arm IDs. This input is not source evidence and must not be presented as an experimental success.

The NVIDIA panel separately shows any real **engineering monomer service check**, its validated artifact fingerprint, request identity and returned confidence. Its interactive structure view draws the actual validated Cα coordinates, colored by chain. Drag to rotate, focus and scroll to zoom, or use arrow keys and +/−; Reset view restores the starting orientation. This is a backbone trace, not a fabricated molecular surface. Download the original validated CIF from the same panel. That engineering receipt does not test the CAR-T hypothesis and is not a matched reference/candidate comparison. Download links appear only when supplied by the service.

A model-recommended public CD19 structure follow-up may appear as a separate approved NVIDIA operation. Its displayed scope and prerequisite checks remain authoritative: exploratory wild-type/exon-2-deleted monomer context does not establish CAR recognition, binding affinity or cellular efficacy. The structure selector keeps service checks and investigation artifacts labeled separately.

Use **View validated structure** on a follow-up card to open its returned artifact directly. A completed individual structure can be inspected while another prediction is pending or its scientific review is running. That partial artifact does not mean the comparison or next decision is complete; preserve the operation's displayed status.

For a real matched BioNeMo demonstration, supply scientist-qualified exact target, reference and candidate sequences and target-retained attestation. Submit the explicit comparison or use qualified live intake inputs. Show actual action identifiers, matching input hashes, validated structures and returned metrics only after they exist. Pending or failed jobs remain pending or failed. No sequence presets or fixture predictions substitute for a real result, and structural confidence does not establish CAR-T efficacy.

## If a dependency is unavailable

Leave the precise provider or data status visible. Choose **Offline walkthrough · no model calls** only explicitly and describe it as a scripted workflow with real pinned evidence. An Astra run must remain labeled Astra; a blocked molecular branch demonstrates a qualification gate, not successful NIM inference. Mocked transport tests are software tests, not proof of live vendor execution.

## Follow-up interaction checks

Only the latest decision can start a ready action. Cards remain visible but disabled while another operation runs, for historical versions, when inputs are missing, or while action readiness cannot be verified. The service rechecks readiness and serializes the action; the browser retains its request identity when a response is uncertain. A returned result becomes a new reviewed decision on the same run. Existing decisions and the original user hypothesis remain available.
