# Specialist proposals and BioNeMo awareness

Registered capabilities are visible to the team before final synthesis. The planning tools only record recommendations. The separate [hypothesis governance](HYPOTHESIS-GOVERNANCE.md) policy lets a reviewer select one qualified follow-up for automatic continuation on newly opted-in live runs. Installed instructions and mocked tests do not establish that a live model has demonstrated useful autonomous selection.

## Role behavior

Every model-driven role receives its pinned role skill, shared `discovery-planning` skill, and a compact case-specific `available_followup_options` payload. `list_available_followups` refreshes scientific readiness after new evidence arrives. The view separates pinned input availability, provider configuration and already accepted results; listing an option is not permission or evidence of execution.

Bioinformatics qualifies measurements and sequence/transcript mappings; statistics evaluates the contrast and uncertainty; molecular science evaluates structural relevance and model limitations. Current process contract `team-tbd-resistance-4` retains the bioinformatics-to-statistics/molecular route introduced in version 3 and requires molecular science to consume that product. Clinical, pharmacology, translational and assay roles retain their distinct questions and responsibilities. Missing exposure data still produces a deterministic blocked pharmacology product, without pretending that a model acted.

All roles can call `propose_followup(analysis_id, scientific_question, rationale, decision_it_could_change, evidence_ids)`. The scientific rationale should explain competing outcomes, a useful discriminator, prerequisites and return checks. The server supplies the role, case, recipe identity, exact input versions and next owner. The proposal can only name an actual registered recipe and accepted evidence. Unknown identifiers and fabricated citations fail. A source-identical completed recipe is returned as already available rather than recorded as new work. A role can retain at most three distinct proposals.

Proposals are attached to the sender's work product. Only proposals from accepted handoffs reach subsequent model context or final `metadata.followup_proposals`. A rejected attempt is not exposed downstream. Independently validated proposals remain in the bounded repair context and are revalidated before the repaired handoff can be accepted; an unrelated prose repair must not silently erase the proposed work. Handoff acceptance checks proposal identities, versions and citations. The coordinator and reviewer are instructed to recommend, defer with a prerequisite, or decline substantive proposals with a scientific explanation. This disposition is a model review obligation, not a deterministic guarantee of scientific judgment.

## NVIDIA scope

The implemented service is NVIDIA BioNeMo Boltz-2. The molecular specialist's existing trusted binder comparison remains available when its exact inputs qualify. Public-sequence monomer recipes are a separate catalog option, with independent reference requirements. Missing binder sequences should not hide such a recipe, while a monomer cannot answer a binding experiment. Bioinformatics, statistics, molecular, translational, assay, coordinator and reviewer roles may load the attributed Boltz2 skill. Broader examples in that vendor skill do not create unimplemented services.

Select prediction only when the possible result informs a structural question. Missing splice estimates, cohort contrasts or reproduction calculations often call for data analysis instead. Skills explicitly separate numerical reproduction from repeating paper conclusions, and unperformed analysis or missing readers from truly unavailable data. They do not contain a preferred hypothesis or expected CD19 answer.

## Execution boundaries and handoff

The two planning tools never call an analysis executor, OpenAI or NVIDIA. Existing role-specific analysis tools and bounded reviewer diagnostics can still run within their original authority. Registered follow-up operations require explicit manual selection or a validated reviewer selection under the run's pinned `hypothesis_governance.auto_continue` policy. The latter queues one action after accepted publication, then reviews its evidence in a new whole-team cycle. Recipes restricted to follow-up execution cannot be smuggled into initial analysis or reviewer diagnostics. Unknown or failed attempts are not automatically replayed, and completed same-input work is reused.

The shared and role instructions define scoped `possible`, `probable` and `clearly_ruled_out` judgments, useful discriminating tests and explicit blockers. All roles can recommend a test; coordinator and reviewer maintain the final ledger and its stable user/agent identities. A stopped investigation can retain possible hypotheses. Scientific interpretation and usefulness remain review responsibilities rather than consequences of passing a schema.

`skills/manifest.json` pins current instruction versions and their exact bytes; use it and persisted receipts as the version authority. The attributed vendor skill remains distinct from application execution policy. Historical work products and decisions retain their original receipts. Never update skill files during an active operation; stop the service and retain private runtime state before deployment.

Key implementation files: `app/discovery_planning.py` (planning contracts), `app/hypothesis_governance.py` (ledger validation), `app/providers.py` (SDK tools/context), `app/stage_evaluation.py` (accepted proposal boundary), `app/process_contract.py` (routes/policy), and `skills/`. Offline tests cover qualification, forged inputs, no execution from proposals, accepted handoff propagation, rejection isolation and repair, governance history and skill integrity. See `VALIDATION.md` for actual results. Real model selection quality and whether the new instructions cause useful NVIDIA recommendations remain untested until a separately requested live run.
