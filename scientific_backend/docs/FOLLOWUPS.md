# Findings and executable discovery follow-ups

Specialists now receive the registered options before synthesis and can attach validated proposals to accepted handoffs. See [discovery planning](DISCOVERY-PLANNING.md) for the proposal tools, role routing and scope. Listing or proposing work does not execute it; the selection/execution contract below remains in force.

The coordinator and independent reviewer now return `insights` and `followups` as part of the strict investigation schema. An insight contains a concise finding, why it matters, accepted evidence IDs and a next step. A recommendation names a registered recipe, rationale, decision it could change, explicit prerequisites and requested readiness. The publication boundary rejects invented recipe identifiers, unaccepted citations and oversized text. The server owns recommendation IDs and executable readiness.

`GET /api/runs/{run_id}/followups` returns the latest decision version, current action readiness and durable operation history. Model-authored recommendations use `origin: model_recommendation`. Available recipes omitted by a model, including options for historical decisions that predate the new schema, use `origin: registered_catalog`. Historical content is not rewritten to invent model authorship.

New live process contracts enable [hypothesis governance](HYPOTHESIS-GOVERNANCE.md). The reviewer selects at most one ready, unperformed registered action in `decision.governance`, tied to named possible/probable hypotheses and a discriminating reason. Accepted publication and the next queued operation commit together; current prerequisites and prior attempts are rechecked at that boundary. `followup_operations[].origin` records `agent_governance` for this path and `scientist_selection` for manual requests. Recommendation authorship and execution selection are separate facts. Proposal tools themselves still submit no work, and older pinned contracts do not acquire automatic authority.

`POST /api/runs/{run_id}/followups` accepts only `decision_version`, `recommendation_id` and `idempotency_key`. The current run must be completed and live. An exact retry resolves to the existing operation; altered payloads, stale decisions and concurrent operations conflict. A selected recipe's content hash, source-manifest hash, original-hypothesis hash and decision hash are frozen in its operation record. Models never supply execution code, filesystem paths, endpoints or sequences to this route.

The worker saves durable intent before execution. A successful result passes the existing evidence acceptance boundary before the team receives it. The specialist and reviewer loop runs against the selected result and compact previous decision; bioinformatics reads the completed analysis instead of being required to repeat broad discovery. Additional bounded reviewer diagnostics remain available. The next decision is a new immutable version on the same run, with the original hypothesis unchanged. Provider usage, applied skills, handoffs and stage evaluations belong to the new operation.

In the automatic path, the reviewed next decision either selects another informative eligible action or records a specific stop reason. `governance_state` and `governance_transitions` distinguish the published plan from actual queued/running/stopped execution. Source/provider changes, cancellation or an existing durable attempt can suppress continuation without rewriting the scientific decision. A completed or attempted identical recipe/source version is never automatically resubmitted. Unknown provider state stops new work pending reconciliation; failure is not counterevidence against a biological mechanism. A manual modeling-only update preserves prior governance as unassessed history and does not start a new scientific continuation cycle.

New recipes declare exact `input_sources` pins in their registry entries. An older snapshot missing any required source or containing another version is marked `needs_inputs` with a fresh-investigation instruction. Neither the readiness endpoint nor execution silently hydrates old snapshots. Accepted recipes are shown as completed instead of offered as independent new evidence.

## Scientific execution scopes

- `data_analysis` dispatches a registered `analyze_case(case_id, analysis_id)` implementation. Computation is deterministic and source-pinned; selecting analyses and reviewing their meaning use the real configured model.
- `bionemo_public_structure` dispatches `structural_followups.execute`. The `cd19-exon2-structure` recipe derives public CD19 WT and exon-2-deleted ectodomains from author exon annotation and a pinned canonical sequence. It submits two actual NVIDIA monomer predictions. This is exploratory structural context; it does not predict RNA splicing, CAR binding, trafficking or clinical efficacy.
- The existing exact target/reference/candidate binder comparison remains a separate qualified path. Its target-retention and construct requirements are unchanged. A molecular specialist may review accepted public monomer evidence without those binder inputs, while keeping the binder comparison blocked.

Only verified complete prediction pairs enter scientific evidence. If one member is pending or unknown, the action retains that status and does not resubmit automatically. Completed individual member artifacts remain viewable as partial outputs, with provider request IDs; they do not create a completed comparison or a new decision. Explicit cancellation likewise does not prove a submitted remote job stopped.

`followup_operations` exposes action ID, status, result status, accepted evidence ID, subsequent decision version, sanitized provider receipts and registered artifact URLs. Structural files are visible while the team is reviewing. Downloads and `/api/runs/{run_id}/structure-preview/{action_id}/{file_path}` share run/action ownership, published-path, no-symlink and SHA checks. Preview geometry is extracted from the actual CIF. The separate engineering monomer check uses `/api/engineering/bionemo/{check_id}/preview.json` and remains outside CAR-T scientific evidence.

## Engineer validation

Run `.venv/bin/python -m pytest tests/test_followups.py tests/test_providers.py tests/test_structural_followups.py tests/test_structure_preview.py -q`. The tests cover receipt validation, actual source mapping, full SDK role execution over explicitly mocked transport, citation and recipe rejection, immutable versions, retry identity, pending jobs, partial output visibility, source-snapshot incompatibility and tampered artifact rejection. They do not establish live provider success or scientific causality; record real requests separately in `VALIDATION.md`.

Aggregate budgets remain advisory by default. Technical response limits, role scope, evidence qualification and actual provider failures remain separate execution boundaries. Automatic and manual follow-ups reuse the same worker lease and durable operation/action system; no parallel worker or unrestricted job path is introduced. Contract tests validate this machinery, not the scientific adequacy of an autonomous sequence of tests.
